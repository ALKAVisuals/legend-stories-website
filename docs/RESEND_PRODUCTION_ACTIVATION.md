# LegendMural Resend production activation

Last reviewed: 18 August 2026.

Purpose: prepare the statutory withdrawal acknowledgement sender without turning it on accidentally. This document does **not** authorize DNS changes, API-key creation, Netlify production secrets or production sending by itself.

## 1. Runtime contract

The tracked withdrawal Function activates Resend only when both of these server-side values exist:

- `RESEND_API_KEY`
- `RESEND_FROM`

Optional:

- `RESEND_REPLY_TO` — routes customer replies to the approved customer-operations mailbox without requiring the technical sending address itself to receive mail.

If API key/from are absent, the durable withdrawal + acknowledgement snapshot still remains available and delivery is reported unavailable/pending rather than silently pretending an email was sent.

The same optional `RESEND_REPLY_TO` value is used by the controlled operator retry script so initial delivery and a later resend use the same reply routing.

## 2. Sending domain decision

Preferred production pattern: use a dedicated LegendMural sending subdomain, for example `mail.legendmural.com`, rather than mixing transactional sending reputation directly with the root domain.

Final domain/subdomain must be explicitly approved before DNS changes.

In Resend:

1. Add the selected owned domain/subdomain.
2. Copy the exact DNS records generated by the Resend dashboard to the authoritative DNS provider; do not invent SPF/DKIM/MX values from examples.
3. Wait until Resend reports the domain verified.
4. The `from` address used by `RESEND_FROM` must match the verified domain/subdomain exactly.
5. Optional DMARC can be added after the required Resend verification records are correct.

Do not configure production `RESEND_FROM` against an unverified or different domain.

## 3. Proposed identity pattern

A production identity should be explicit and customer-recognizable, for example:

`LegendMural <withdrawals@mail.legendmural.com>`

This is a proposed pattern, not an activated address.

`RESEND_REPLY_TO` should point at the customer-operations mailbox that is actually monitored. Until a dedicated LegendMural mailbox is confirmed, do not invent a mailbox solely for appearance.

## 4. API key least privilege

Create a dedicated production key only when activation is approved.

Required policy:

- use Resend **Sending access**, not Full access, unless a separately documented operation truly needs broader permissions;
- restrict the key to the selected LegendMural sending domain when Resend account controls allow it;
- give it a clear name such as `LegendMural Production Withdrawal`;
- copy the token once into the Netlify Production secret and do not paste it into chat, GitHub, screenshots or source files;
- never reuse a browser/client-side key;
- rotate deliberately rather than deleting an active key before the replacement has been proven.

## 5. Netlify values — activation day

Production only unless a separate non-production test context is intentionally configured:

- `RESEND_API_KEY` — secret, server-side;
- `RESEND_FROM` — approved verified sender identity;
- `RESEND_REPLY_TO` — approved monitored operations address.

Do not set these as part of the first Gate 6 database/PayPal Sandbox deployment. Gate 3 activation is a separate step.

After adding/changing Netlify environment values, a new deployment/configuration activation must occur before treating the runtime as updated.

## 6. Controlled non-production proof

Before production sending is considered ready:

1. Use the final verified sending identity and a scoped test API key/context.
2. Submit one controlled withdrawal against a synthetic/test order in an isolated non-production data set.
3. Verify the durable withdrawal registration exists.
4. Verify the durable acknowledgement snapshot exists before delivery state changes.
5. Verify Resend accepts the message and a provider message ID is recorded.
6. Verify the actual inbox receives the message.
7. Verify Resend reports a successful delivery event/state for that message.
8. Verify the email contains:
   - consumer name;
   - Order ID;
   - confirmation email address;
   - statutory withdrawal declaration snapshot;
   - confirmation code;
   - server receipt date/time;
   - statement that acknowledgement does not itself prove refund completion.
9. Reply to the email and verify the reply reaches the approved operations mailbox when `RESEND_REPLY_TO` is configured.
10. Inspect Function logs and confirm no API key, full message body or unnecessary customer payload is logged.

## 7. Failure/retry proof

Before Gate 3 GO, exercise one controlled delivery failure in non-production:

1. withdrawal + acknowledgement snapshot must remain durable;
2. delivery state becomes failed/pending as designed;
3. statement snapshot must not be rewritten;
4. operator can identify the case by canonical confirmation code;
5. after the failure cause is fixed, run the controlled retry script with the same durable snapshot;
6. retry must use the same confirmation code/idempotency identity;
7. once the acknowledgement is recorded as sent, the script refuses another duplicate resend by default.

Do not delete/recreate the withdrawal merely to retry an email.

## 8. Provider retention/privacy acceptance

Production activation must acknowledge the actual Resend account/service behavior rather than claim zero retention by default.

Current reviewed provider position:

- Resend's DPA describes email recipients, addresses, metadata and message content as customer data processed for email delivery;
- the DPA states customer data is processed while the agreement is active and user/customer data is deleted within 90 days after termination;
- Resend offers a separate option to disable message-content storage only for qualifying Pro/Scale customers with additional conditions/cost; this is not assumed for LegendMural launch preparation;
- the public LegendMural Privacy notice must continue to describe Resend and international processing accurately.

Gate 3 remains NO-GO until this operational retention position is explicitly accepted for the production account.

## 9. Production activation acceptance criteria

Gate 3 can become GO only when all are true:

- selected sending domain/subdomain verified;
- final `RESEND_FROM` approved;
- final monitored `RESEND_REPLY_TO` approved;
- least-privilege production API key created and stored server-side;
- provider retention/logging position accepted;
- controlled non-production delivery + reply routing passed;
- controlled failure + resend passed;
- production secrets then activated intentionally;
- one controlled production acknowledgement is delivered and correlated to its durable acknowledgement record;
- logs contain no secrets or unnecessary customer payload.

Until then, Resend production sending remains intentionally inactive.
